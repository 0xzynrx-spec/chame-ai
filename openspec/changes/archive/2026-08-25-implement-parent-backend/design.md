## Context

现有系统已有完整的家长模型（Parent）和绑定模型（StudentParentBinding），但缺少家长端 API 和服务层。预警服务（early_warning.py）已有 `notified_parent` 标记但未实际创建通知记录。LLM 服务已有 `_call_model()` 基础设施，可复用。

## Goals / Non-Goals

**Goals:**
- 家长可通过手机号注册并绑定学生（原子操作）
- 家长可查看已绑定学生的总览、学情报告、通知
- 周报自动生成并缓存，每个家长独立接收通知
- 预警触发时自动通知已绑定家长
- 数据权限隔离：家长只能访问已绑定学生的数据

**Non-Goals:**
- AI 助手（Agent 基础设施未建，独立变更）
- LMS 集成（钉钉/企微/LTI/SFTP）
- learning_plan 通知推送（只展示不推送）
- reminder 通知生成（有数据源但无触发条件）

## Decisions

### 1. 注册与绑定原子操作

**决策**: 注册和绑定在同一个事务中完成，使用数据库事务保证原子性。

**理由**: 分开操作会导致"注册成功但绑定失败"的中间状态，用户体验差。原子操作保证要么全部成功，要么全部回滚。

**替代方案**: 先注册后绑定（两步操作）— 增加复杂度，需处理中间状态。

### 2. 周报缓存策略

**决策**: WeeklyReport 表存储周报，每个学生每周一条记录（student_id + week_start 唯一索引）。

**理由**: 避免重复调用 LLM，降低成本。手动触发时 cache-first，定时任务时跳过已有缓存。

**替代方案**: 不缓存，每次调用 LLM — 成本高，响应慢。

### 3. 通知与周报解耦

**决策**: 周报生成后为每个家长创建独立的 ParentNotification 记录，而不是共享一条通知。

**理由**: 每个家长的通知状态独立（已读/未读），未来可支持个性化通知渠道。

**替代方案**: 共享通知记录 — 无法独立管理已读状态。

### 4. 数据权限校验

**决策**: 每个家长端 API 都校验 StudentParentBinding 表，确认家长有权访问该学生数据。

**理由**: 安全性要求，防止家长通过猜测 student_id 访问他人数据。

**替代方案**: 只在登录时校验 — 无法防止 ID 遍历攻击。

### 5. 学生端绑定码展示位置

**决策**: 在「我的」页面新增"家长绑定"菜单项，点击展开绑定码和已绑定家长列表。

**理由**: 符合用户直觉，绑定码属于个人信息管理范畴。

**替代方案**: 独立设置页面 — 功能不值得单独页面。

### 6. LLM 调用复用

**决策**: 复用现有 `_call_model()` 函数，通过不同 Prompt 生成周报和学情特点。

**理由**: 避免重复造轮子，统一 LLM 调用入口。

### 7. 定时任务集成

**决策**: 在现有 scheduler.py 中新增周报定时任务，每周一 08:00 UTC 执行。

**理由**: 复用现有 APScheduler 基础设施，统一管理定时任务。

## Risks / Trade-offs

**[风险] LLM 生成质量不稳定** → 使用结构化 Prompt + JSON Schema 约束输出格式，添加后处理验证。

**[风险] 周报定时任务超时** → 使用异步任务队列（可选），或限制单次生成数量。

**[风险] 绑定码碰撞** → 6 位数字有 100 万种组合，碰撞概率低，且有唯一索引保护。

**[权衡] 缓存一致性** → 周报缓存可能与最新数据不一致，但每周更新一次可接受。

**[权衡] 通知数量** → 每个家长独立通知，多家长场景下通知数量线性增长，可接受。
